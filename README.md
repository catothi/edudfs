# EduDFS – a teaching distributed file system in Java, inspired by HDFS

EduDFS is a deliberately small teaching implementation of a distributed file system whose **architecture
is inspired by Apache Hadoop HDFS** (Hadoop 3.x). Class, method and field names follow the original,
so that you can find the corresponding code afterwards in the real codebase (`hadoop-hdfs-project/`).
EduDFS is written from scratch and contains no Apache Hadoop source code.
There are no external dependencies; all you need is Java 21 or newer.

> EduDFS is an independent project. It is **not** affiliated with, endorsed by, or sponsored by the
> Apache Software Foundation. In this documentation, “the original” always means Apache Hadoop HDFS.

## Quick start

```bash
./hdfs build                # compile into out/ (only javac needed)
./hdfs demo                 # guided tour through all core concepts (~1 min)
./hdfs minicluster 3        # NameNode + 3 DataNodes in one JVM (runs until Ctrl+C)
```

The commands below run in a **second terminal** while the minicluster is running.
If you have changed the code, you must restart the minicluster (`./hdfs build` first).

You can also start everything in separate processes: `./hdfs namenode` and
`./hdfs datanode <root> <xferPort> <ipcPort>` (`<root>` = directory that represents the DataNode's “machine”).
Alternatively, `mvn compile` builds the project.
Tests (121 of them, approx. 45 s): `./hdfs test` or `mvn test` – stop a running minicluster first,
because the tests use the same ports.

## Configuration

As in the original, all processes read the **same** files `conf/core-site.xml` and `conf/hdfs-site.xml`
(Hadoop format). The most important setting for the disks:

```xml
<name>dfs.datanode.data.dir</name>
<value>[DISK]/data/1/dfs/dn,[DISK]/data/2/dfs/dn</value>     <!-- 2 disks (volumes) per DataNode -->
```

Because all DataNodes run on one machine here, each one has its own root directory (`data/dn<i>/`) under
which these paths live. Individual values can be overridden with `-Dname=value`, e.g.
`JAVA_OPTS="-Ddfs.replication=2" ./hdfs minicluster 3`. All keys: [Section 10](docs/DOCUMENTATION.md#10-configuration).

## Commands

The project directory contains the sample file `demo.txt` with the content `This is a test 234 test`.
The command names match `hdfs dfs` from the original.

```bash
# local -> HDFS
./hdfs dfs -mkdir /user/me
./hdfs dfs -copyFromLocal demo.txt /user/me/demo.txt    # equivalent: -put
./hdfs dfs -put -f demo.txt /user/me/demo.txt           # -f: overwrite existing file

# inspect
./hdfs dfs -ls -R /
./hdfs dfs -cat /user/me/demo.txt
./hdfs dfs -metasave                                    # INodes, blk IDs, leases, DataNodes

# append
./hdfs dfs -appendToFile demo.txt /user/me/demo.txt     # append a local file
echo "one more line" | ./hdfs dfs -appendToFile - /user/me/demo.txt   # '-' = stdin
(head -c 100000 /dev/urandom; sleep 30) | ./hdfs dfs -appendToFile - /user/me/demo.txt   # watch rbw/ for 30 s

# HDFS -> local
./hdfs dfs -copyToLocal /user/me/demo.txt demo-copy.txt   # equivalent: -get

# delete
./hdfs dfs -rm /user/me/demo.txt                        # a single file
./hdfs dfs -rm -r /user                                 # directory, recursively
./hdfs dfs -rm -r '/*'                                  # EVERYTHING under / (quotes required!)

# try out lease recovery
./hdfs dfs -writeAndCrash /user/me/x.bin 100000         # simulate a client crash
./hdfs dfs -recoverLease /user/me/x.bin
```

* `'/*'` must be quoted, otherwise the local shell replaces the `*` with the files
  of the **local** root directory. `/` itself cannot be deleted (as in the original).
* `-skipTrash` is accepted but has no effect, because there is no trash.
* Append always appends the new data in a **new block** (like `append` with `CreateFlag.NEW_BLOCK`
  in the original). After two appends `demo.txt` therefore has three small blocks – visible with `-metasave`.
* The command with `sleep 30` deliberately keeps the write open: `head` sends 100,000 bytes immediately,
  `sleep` then keeps the pipe open for 30 s, and `appendToFile -` only closes the file once the pipe is closed.
  During that time the new block is in `rbw/`, afterwards in `finalized/`. The command therefore takes at least as long
  as the `sleep`. Flow and limitations: [Section 8.9.1](docs/DOCUMENTATION.md#891-watching-rbw--finalized).

## Where is the data? What survives a restart?

| | where | persistent? |
|---|---|---|
| Namespace (directories, files, block IDs) | only in the NameNode's RAM | **no** – the original writes FSImage + EditLog, that is missing here |
| Block contents | on the DataNodes' volumes: `data/dn<i>/data/<n>/dfs/dn/current/BP-…/current/finalized/subdirX/subdirY/blk_<id>` + `blk_<id>_<GS>.meta` | **yes**, regular files on disk |
| Identity of a DataNode and its disks | `data/dn<i>/data/<n>/dfs/dn/current/VERSION` (`datanodeUuid`, `storageID`) | yes |

Layout of a DataNode directory (explained in [Section 6](docs/DOCUMENTATION.md#62-directory-layout-of-a-volume)):

```
data/dn0/                                   root of DataNode 0's “machine”
├── data/1/dfs/dn/                          disk 1 = 1st entry in dfs.datanode.data.dir
│   └── current/
│       ├── VERSION                         storageID=DS-…, clusterID, datanodeUuid
│       └── BP-1-127.0.0.1-1700000000000/   block pool
│           └── current/
│               ├── VERSION
│               ├── finalized/subdir0/subdir0/blk_1073741825, blk_1073741825_1001.meta
│               └── rbw/                    replicas currently being written
└── data/2/dfs/dn/…                         disk 2, same layout
```

You can simulate a disk failure while the minicluster is running: `rm -rf data/dn0/data/2` – the DataNode
keeps running, the NameNode only has the blocks of this disk re-replicated (`./hdfs dfs -metasave`).

What this means on restart (covered by the tests `restartedDataNodeReportsItsReplicasAgain` /
`nameNodeRestartLosesNamespaceAndOrphanBlocksAreDeleted` in `MiniDFSClusterTest`):

* **Only one DataNode restarts:** Its blocks are preserved. It reports them via a block report,
  and the files are fully readable again.
* **The NameNode or the whole minicluster restarts:** The namespace is empty (`-ls /` shows nothing).
  The DataNodes report their old blocks, but they no longer belong to any file. The NameNode therefore has them
  deleted (`does not belong to any file -> invalidate`), and **a few seconds later the block files
  on disk are gone as well**.

So there are two ways to clean up:

```bash
./hdfs dfs -rm -r '/*'     # with the cluster running: delete everything, the DataNodes clean up their disks
rm -rf data/               # with the cluster stopped: remove the DataNode directories completely
```

Background (block reports, invalidate, comparison with FSImage/EditLog): [Section 8.8](docs/DOCUMENTATION.md#88-restart-what-survives).
