# EduDFS – a teaching distributed file system in Java, inspired by HDFS

EduDFS is a deliberately small teaching implementation of a distributed file system whose **architecture
is inspired by Apache Hadoop HDFS** (Hadoop 3.x). Class, method and field names follow the original,
so that you can find the corresponding code afterwards in the real codebase (`hadoop-hdfs-project/`).
EduDFS is written from scratch and contains no Apache Hadoop source code.
There are no external dependencies; all you need is Java 21 or newer.

> EduDFS is an independent project. It is **not** affiliated with, endorsed by, or sponsored by the
> Apache Software Foundation. In this documentation, “the original” always means Apache Hadoop HDFS.

## Quick start

```bash
./hdfs build
./hdfs demo
./hdfs minicluster 3
```

`build` compiles into `out/` (only `javac` needed), `demo` is a guided tour through all core concepts (~1 min),
and `minicluster 3` starts a NameNode + 3 DataNodes in one JVM (runs until Ctrl+C).

**macOS / zsh:** zsh does not treat `#` as a comment when you paste commands, so pasted comments become
arguments. The commands in this README contain no comments, but if you copy shell snippets from elsewhere,
enable comments for the current terminal:

```bash
setopt interactivecomments
```

or permanently for all new terminals:

```bash
echo 'setopt interactivecomments' >> ~/.zshrc
```

The commands below run in a **second terminal** while the minicluster is running.
If you have changed the code, you must restart the minicluster (`./hdfs build` first).

You can also start everything in separate processes: `./hdfs namenode` and
`./hdfs datanode <root> <xferPort> <ipcPort>` (`<root>` = directory that represents the DataNode's “machine”).
Alternatively, `mvn compile` builds the project.
Tests (163 of them – 126 EduDFS, 37 EduDFSBase – approx. 60 s): `./hdfs test` or `mvn test` – stop a running
minicluster first, because the tests use the same ports.

## Configuration

As in the original, all processes read the **same** files `conf/core-site.xml` and `conf/hdfs-site.xml`
(Hadoop format). The most important setting for the disks:

```xml
<name>dfs.datanode.data.dir</name>
<value>[DISK]/data/1/dfs/dn,[DISK]/data/2/dfs/dn</value>     <!-- 2 disks (volumes) per DataNode -->
```

Because all DataNodes run on one machine here, each one has its own root directory (`data/dn<i>/`) under
which these paths live. Individual values can be overridden with `-Dname=value`, e.g.
`JAVA_OPTS="-Ddfs.replication=2" ./hdfs minicluster 3`. All keys: [Section 10](docs/DOCUMENTATION.md#10-configuration).

## Commands

The project directory contains the sample file `demo.txt` with the content `This is a test 234 test`.
The command names match `hdfs dfs` from the original.

**Local → HDFS** (`-put` is equivalent to `-copyFromLocal`; `-f` overwrites an existing file):

```bash
./hdfs dfs -mkdir /user/me
./hdfs dfs -copyFromLocal demo.txt /user/me/demo.txt
./hdfs dfs -put -f demo.txt /user/me/demo.txt
```

**Inspect** (`-metasave` prints INodes, block IDs, leases and DataNodes):

```bash
./hdfs dfs -ls -R /
./hdfs dfs -cat /user/me/demo.txt
./hdfs dfs -metasave
```

**Append** – a local file, stdin (`-`), and a write held open for 30 s so you can watch `rbw/`:

```bash
./hdfs dfs -appendToFile demo.txt /user/me/demo.txt
echo "one more line" | ./hdfs dfs -appendToFile - /user/me/demo.txt
(head -c 100000 /dev/urandom; sleep 30) | ./hdfs dfs -appendToFile - /user/me/demo.txt
```

**HDFS → local** (`-get` is equivalent to `-copyToLocal`):

```bash
./hdfs dfs -copyToLocal /user/me/demo.txt demo-copy.txt
```

**Delete** – a single file, a directory recursively, and **everything** under `/` (quotes required!):

```bash
./hdfs dfs -rm /user/me/demo.txt
./hdfs dfs -rm -r /user
./hdfs dfs -rm -r '/*'
```

**Try out lease recovery** – `-writeAndCrash` simulates a client crash:

```bash
./hdfs dfs -writeAndCrash /user/me/x.bin 100000
./hdfs dfs -recoverLease /user/me/x.bin
```

* `'/*'` must be quoted, otherwise the local shell replaces the `*` with the files
  of the **local** root directory. `/` itself cannot be deleted (as in the original).
* `-skipTrash` is accepted but has no effect, because there is no trash.
* Append always appends the new data in a **new block** (like `append` with `CreateFlag.NEW_BLOCK`
  in the original). After two appends `demo.txt` therefore has three small blocks – visible with `-metasave`.
* The command with `sleep 30` deliberately keeps the write open: `head` sends 100,000 bytes immediately,
  `sleep` then keeps the pipe open for 30 s, and `appendToFile -` only closes the file once the pipe is closed.
  During that time the new block is in `rbw/`, afterwards in `finalized/`. The command therefore takes at least as long
  as the `sleep`. Flow and limitations: [Section 8.9.1](docs/DOCUMENTATION.md#891-watching-rbw--finalized).

## Where is the data? What survives a restart?

| | where | persistent? |
|---|---|---|
| Namespace (directories, files, block IDs) | only in the NameNode's RAM | **no** – the original writes FSImage + EditLog, that is missing here |
| Block contents | on the DataNodes' volumes: `data/dn<i>/data/<n>/dfs/dn/current/BP-…/current/finalized/subdirX/subdirY/blk_<id>` + `blk_<id>_<GS>.meta` | **yes**, regular files on disk |
| Identity of a DataNode and its disks | `data/dn<i>/data/<n>/dfs/dn/current/VERSION` (`datanodeUuid`, `storageID`) | yes |

Layout of a DataNode directory (explained in [Section 6](docs/DOCUMENTATION.md#62-directory-layout-of-a-volume)):

```
data/dn0/                                   root of DataNode 0's “machine”
├── data/1/dfs/dn/                          disk 1 = 1st entry in dfs.datanode.data.dir
│   └── current/
│       ├── VERSION                         storageID=DS-…, clusterID, datanodeUuid
│       └── BP-1-127.0.0.1-1700000000000/   block pool
│           └── current/
│               ├── VERSION
│               ├── finalized/subdir0/subdir0/blk_1073741825, blk_1073741825_1001.meta
│               └── rbw/                    replicas currently being written
└── data/2/dfs/dn/…                         disk 2, same layout
```

You can simulate a disk failure while the minicluster is running: `rm -rf data/dn0/data/2` – the DataNode
keeps running, the NameNode only has the blocks of this disk re-replicated (`./hdfs dfs -metasave`).

What this means on restart (covered by the tests `restartedDataNodeReportsItsReplicasAgain` /
`nameNodeRestartLosesNamespaceAndOrphanBlocksAreDeleted` in `MiniDFSClusterTest`):

* **Only one DataNode restarts:** Its blocks are preserved. It reports them via a block report,
  and the files are fully readable again.
* **The NameNode or the whole minicluster restarts:** The namespace is empty (`-ls /` shows nothing).
  The DataNodes report their old blocks, but they no longer belong to any file. The NameNode therefore has them
  deleted (`does not belong to any file -> invalidate`), and **a few seconds later the block files
  on disk are gone as well**.

So there are two ways to clean up:

* With the cluster running, delete everything – the DataNodes clean up their disks:

  ```bash
  ./hdfs dfs -rm -r '/*'
  ```

* With the cluster stopped, remove the DataNode directories completely:

  ```bash
  rm -rf data/
  ```

Background (block reports, invalidate, comparison with FSImage/EditLog): [Section 8.8](docs/DOCUMENTATION.md#88-restart-what-survives).

## EduDFSBase: a wide column store on top of EduDFS

The package `edudfsbase` adds a teaching implementation of **HBase** (Apache HBase 2.x) that stores all its data in
EduDFS: HMaster, RegionServers, regions, MemStore, WAL, HFiles with a multi-level block index (B+ tree) and Bloom filter, BlockCache,
flushes, compactions and crash recovery via WAL splitting. As in EduDFS, the class names follow the original.

**HFiles and WALs are written as text**, so you can watch them with `./hdfs dfs -cat` – the original writes
them binary (Protobuf). Everything else – layout, block magics, reading from the trailer – follows the original.

```bash
./hdfs minicluster 3
./hbase minicluster 2
./hbase shell
```

The first two commands each run in their own terminal. In the shell:

```
create 'users', {NAME => 'info', VERSIONS => 3}, SPLITS => ['m']
put 'users', 'alice', 'info:name', 'Alice Adams'
flush 'users'
get 'users', 'alice', {TRACE => true}
scan 'users', {RAW => true, VERSIONS => 10, SOURCE => true}
metasave
```

Look inside the files with `./hbase hfile --layout -m -f <path>` and `./hbase wal -p <path>`; the guided tour
`./hbase demo` runs through everything including a RegionServer crash. For a large HFile with a 3-level block index:

```bash
./hbase pe --rows=3000 --compact sequentialWrite 1
./hbase hfile -m -f '/hbase/data/default/TestTable/*/info/*'
./hbase hfile --tree -f '/hbase/data/default/TestTable/*/info/*'
./hbase hfile --html hfile.html -f '/hbase/data/default/TestTable/*/info/*'
open hfile.html                                        # macOS; Linux: xdg-open hfile.html
```

`pe … --compact` leaves exactly one HFile in `TestTable`, so the `*` (resolved in HDFS – keep the quotes) matches it;
`pe` also prints the full path.

`./hbase demo index` shows the same in its own cluster. Everything else:
**[docs/EDUDFSBASE.md](docs/EDUDFSBASE.md)**.

## Parquet hands-on: columnar files in EduDFS

Apache Parquet files in EduDFS, read with Python (pyarrow) through a WebHDFS gateway (`./hdfs httpfs`, port 14000).
Every byte range the Parquet reader asks for is logged – so you can watch **projection and predicate pushdown**,
the effect of **ORDER BY**, **column partitioning** and the **encodings**, step by step, on a sample data set of
200,000 orders. PySpark is not needed. Full documentation: **[docs/PARQUET.md](docs/PARQUET.md)**.

### The data model

One table, `orders`: **one row = one order of one product** in an online shop in 2025 (200,000 rows, generated
deterministically by `src/main/python/dataset.py`). Conceptually it is a fact table of a star schema whose dimensions
(time, geography, product, customer) are denormalized into the row – the typical shape of analytical data in a data
lake, and the shape Parquet is built for: many rows, few columns per query.

```
orders  (fact table, 200,000 rows)
│
├── key         order_id        int64      1, 2, 3, …                     ascending
├── time        order_ts        timestamp  2025-01-01 … 2025-12-31        arrival order = ascending
├── geography   country         string     9 values (DE 30 %)
│               city            string     ~30 values                     depends on country
├── product     category        string     8 values
│               product         string     48 values
│               unit_price      double     75 prices                      sometimes −20 %
├── measure     quantity        int32      1 … 5
├── customer    customer_email  string     ~40,000 values, 8 % NULL
└── state       status          string     delivered 85 %, returned, cancelled, shipped

revenue of a row = unit_price * quantity
```

The columns are chosen so that each Parquet feature has something to show: `order_id`/`order_ts` are ascending
(delta encoding; min/max per row group are narrow, so filters on time skip data), `country`/`status` have few values
(dictionary + RLE; good partition key), `customer_email` has many values and NULLs (definition levels), and the
value `status = 'refunded'` does not exist (where min/max fails and Bloom filters would help).

The same data is stored in several layouts:

| Path in EduDFS | Layout | Created by |
|---|---|---|
| `/shop/orders.csv` | CSV, 21 MB | `./parquet demo 1` |
| `/shop/orders.parquet` | Parquet, time order, 8 row groups of 25,000 rows, 4.9 MB | `./parquet demo 1` |
| `/shop/orders_sorted.parquet` | Parquet, `ORDER BY country, order_ts` | `./parquet demo 5` |
| `/shop/orders_by_country/country=XX/` | partitioned by country (9 files) | `./parquet demo 6` |
| `/shop/orders_tuned.parquet` | sorted + delta encodings + zstd, 2.4 MB | `./parquet demo 7` |
| `/shop/orders_nested.parquet` | a separate, nested example: tags (list), items (list of structs), packages (list of lists) | `./parquet nested` |
| `/bench/…` | shuffled, partitioned by country + day (~3,300 files), 1 … 1,024 files, 1,000 … 200,000 rows per row group | `./parquet web` (on first run) |

### Example queries

| # | SQL | What happens in the Parquet reader |
|---|---|---|
| 1 | `SELECT sum(unit_price * quantity) FROM orders` | projection: only 2 of 10 columns are read; nothing can be skipped |
| 2 | `SELECT country, sum(unit_price * quantity) FROM orders GROUP BY country` | projection: 3 columns |
| 3 | `SELECT category, sum(unit_price * quantity) FROM orders WHERE country = 'DE' AND order_ts >= '2025-12-01' GROUP BY category` | predicate pushdown: 7 of 8 row groups skipped (time order); with partitions only `country=DE/` is opened |
| 4 | `SELECT * FROM orders WHERE order_id = 123456` | point lookup: min/max of `order_id` point to exactly one row group |
| 5 | `SELECT order_id, unit_price FROM orders WHERE country = 'DE'` | in time order: nothing skipped (every row group has AT … US); after `ORDER BY country`: half skipped |
| 6 | `SELECT order_id FROM orders WHERE status = 'refunded'` | 0 rows, but every row group is read: 'refunded' lies between min 'cancelled' and max 'shipped' |

Queries 1–4 are the four queries of the benchmark web UI (with time measurement). Filters and projections
(without aggregation) also run on the command line, e.g. query 5 and 6:

```bash
./parquet query /shop/orders.parquet --columns order_id,unit_price --where "country = 'DE'" --explain
./parquet query /shop/orders_sorted.parquet --columns order_id,unit_price --where "country = 'DE'" --explain
./parquet query /shop/orders.parquet --columns order_id --where "status = 'refunded'"
./parquet query /shop/orders.parquet --columns unit_price --sum unit_price --where "order_ts >= '2025-12-01'"
```

`--where` understands `column op value` (`= != < <= > >=`) joined with `and`; `--explain` shows for every row group
why it is read or skipped; `--no-pushdown` reads everything for comparison.

### Step by step: what to run, and where to look

All commands run in the project directory `edudfs/`.

**0 – once:** compile EduDFS and create the Python environment (`.venv/` with pyarrow):

```bash
./hdfs build
./parquet setup
```

**1 – terminal 1: EduDFS.** NameNode + 3 DataNodes, block size 1 MB. Wait for `MiniDFSCluster running`; runs until Ctrl+C.

```bash
./hdfs minicluster 3
```

**2 – terminal 2: HttpFS.** The REST gateway Python reads through (port 14000). Start it after terminal 1 is ready;
runs until Ctrl+C. **Keep this terminal visible**: every read appears here as `OPEN <file> bytes [from .. to) <- blk_…`.

```bash
./hdfs httpfs
```

**3 – terminal 3: the guided tour.** Run the steps one after another (or `./parquet demo` for all, Enter = next):

```bash
./parquet demo 1
./parquet demo 2
./parquet demo 3
./parquet demo 4
./parquet demo 5
./parquet demo 6
./parquet demo 7
./parquet demo 8
```

| Step | Topic | Where to look |
|---|---|---|
| 1 | the data set, CSV vs. Parquet in EduDFS | `./hdfs dfs -ls -R /shop` – sizes and blocks |
| 2 | inside the file: magic, row groups, column chunks, pages, footer | writes `parquet.html` → `open parquet.html` (Linux: `xdg-open`) |
| 3 | projection pushdown (`SELECT unit_price`) | terminal 2: one footer read, then one request per `unit_price` chunk |
| 4 | predicate pushdown (example queries 3, 5, 6) | the `--explain` lines: `SKIP` / `read` per row group |
| 5 | `ORDER BY country` before writing | now `country = 'DE'` skips row groups; the country column shrinks 100× |
| 6 | partitioning by country | `./hdfs dfs -ls -R /shop/orders_by_country` – 1 of 9 files is read |
| 7 | encodings and compression | the size table; `./parquet view --pages -f /shop/orders_tuned.parquet` |
| 8 | best practices | summary |

**4 – look inside a file** (terminal 3):

```bash
./parquet view -f /shop/orders.parquet
./parquet view --pages -f /shop/orders.parquet
./parquet view -m -f /shop/orders.parquet
./parquet view --html parquet_sorted.html -f /shop/orders_sorted.parquet
open parquet_sorted.html
```

Layout with HDFS blocks, all pages (header, definition levels, values), footer statistics, and the interactive
picture (counterpart of the HFile explorer: the file byte by byte with its HDFS blocks, row groups and column chunks with
their first values, the pages, the min/max table and a pushdown simulator).

**4b – nested data: repetition levels** (terminal 3):

```bash
./parquet nested
open parquet_nested.html
```

A separate example with lists and structs in one field (`tags`, `items`, `packages`). The terminal shows for the first
rows how each entry is stored as repetition level + definition level + value; in the HTML click a column chunk of
`tags` or `packages` – section 4 shows the rows as records, the levels with their meaning and the pages. Details:
[docs/PARQUET.md, 6b](docs/PARQUET.md#6b-nested-data-repetition-and-definition-levels).

**5 – time it: the benchmark web UI** (terminal 3, runs until Ctrl+C):

```bash
./parquet web
```

Open <http://localhost:8050/> in the browser (or <http://localhost:8050/#run> – runs everything by itself). Choose
an example query (1–4) and a storage preset (`local`, `hdfs` = 2 ms per request, `s3` = 25 ms per request –
simulated), then:

* **Run all layouts** – CSV vs. Parquet (time order, shuffled, sorted, partitioned; optionally the ~3,300-file
  layout): time, bytes read, requests, files opened.
* **Run sweep** (number of files, rows per row group) – the sweet spots; switch the preset and run again to get a
  second line.

Missing layouts are written to EduDFS on the first run. Details and measured numbers:
[docs/PARQUET.md, 6a](docs/PARQUET.md#6a-timing-it-the-benchmark-web-ui).

**6 – clean up** (with the cluster running), or stop all terminals with Ctrl+C – the NameNode keeps the namespace
only in memory, so after a restart everything is gone anyway:

```bash
./hdfs dfs -rm -r /shop
./hdfs dfs -rm -r /bench
```
